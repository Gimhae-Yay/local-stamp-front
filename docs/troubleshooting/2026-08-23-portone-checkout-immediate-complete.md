## 기대 결과와 실제 결과

### 기대 결과

결제 버튼을 누르면 PortOne 결제 UI가 열리고, 결제 성공·실패 이후에만 결과 URL로 이동한다.

### 실제 결과

브라우저 캐시와 기록을 삭제한 뒤에도 결제 버튼을 누르면 `/payment/complete?paymentId=<내부 결제 ID>`로 즉시 이동했다. 결제 이후 서버의 PortOne 검증·웹훅 로그는 없었다.

## 재현 절차

### 선행 조건

- 유상 예약 가능한 회차
- 로그인한 방문자

### 명령·요청·입력

1. 예약 선점을 생성한다.
2. 결제 생성 API를 호출한다.
3. 결제 진행 버튼을 누른다.

### 재현 결과

- 실행 횟수: 운영 브라우저에서 반복 보고됨
- 성공 횟수: 0회
- 실패 횟수: 반복 재현
- 종료 코드·HTTP 상태: 결제 생성 API는 `201`, 결제 조회 API는 `200`

## 수집한 증거

- 프론트엔드는 `requestPortOneCheckout()` 반환 뒤 내부 결제 ID로 결과 페이지 이동을 실행했다.
- `redirectUrl`을 전달하면서 `forceRedirect`를 지정하지 않아 PortOne SDK가 반환값 방식과 리다이렉트 방식을 자동 선택할 수 있었다.
- PortOne SDK의 강제 리다이렉트 구현은 결제 성공 또는 실패 콜백에서만 결과 URL을 이동시킨다.
- 기존 단위 테스트는 SDK가 즉시 성공 응답을 반환하도록 mock 처리해 실제 결제 UI 흐름을 검증하지 못했다.

## 근본 원인

- 촉발 조건: PortOne SDK 호출 이후 반환 경로가 실행됨.
- 결함이 있는 코드·설정·데이터·계약: 반환값·리다이렉트 혼합 흐름에서 프론트가 내부 결과 페이지로 직접 이동함.
- 증상으로 이어진 메커니즘: SDK 반환 뒤 내부 결제 ID를 쿼리에 넣어 완료 화면을 즉시 표시함.
- 기존 방어가 막지 못한 이유: 단위 테스트가 SDK의 즉시 성공 반환을 mock하면서 완료 화면 이동을 정상으로 검증함.
- 결론의 증거: 운영 URL의 내부 결제 ID와 프론트 직접 이동 경로가 일치함.

## 해결 또는 완화

- 선택한 방법: `forceRedirect: true`로 결과 전달 방식을 고정하고, 프론트 직접 이동을 제거한다. 내부 결제 ID는 `backendPaymentId`로 분리한다.
- 변경 파일: `src/payments/portone.ts`, `src/pages/ReservationPages.tsx`
- 정책·계약 변경 여부: 없음

## 재발 방지와 문서 반영

- 결제 UI SDK는 실제 브라우저·테스트 채널 검증을 별도로 수행한다.
- 진단 로그에는 결제자 정보나 결제 키를 기록하지 않는다.

## 잔여 위험과 후속 작업

- PortOne 채널의 실제 PG 창 방식과 결제 UI 표시는 운영 또는 테스트 채널에서 별도로 확인해야 한다.
- 강제 리다이렉트 흐름에서 SDK가 반환되면 브라우저 콘솔의 `[PortOne]` 로그로 응답을 확인한다.
