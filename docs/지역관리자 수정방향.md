# 지역 관리자 기능 수정 방향

> 재검증일: 2026-08-21
> 기준: 프론트엔드와 백엔드를 실제 `local` 환경으로 실행한 E2E 결과와 기존 관리자 연동 문제 기록
> 작성 원칙: 이번 재검증에서 근거가 확인된 미해결 항목만 유지한다.
>
> 문서 범위: 지역 관리자 E2E 문제와 아직 남아 있는 플랫폼 관리자 환불 연동 문제를 한곳에서 관리한다.

## 우선순위 요약

| 수정 시점 | 우선순위 | 문제 구분 | 문제 | 담당 수정 대상 |
| --- | --- | --- | --- | --- |
| 크리티컬 | P1 | 로컬 환경·시드 | `local` DB 이름과 시드 안전장치가 맞지 않음 | 백엔드 |
| 일단 고치지 않아도 됨 | P2 | 백엔드 | 예약 없는 환불 상세 조회가 여전히 `500`을 반환할 수 있음 | 백엔드·프론트엔드 |
| 일단 고치지 않아도 됨 | P2 | API 계약·문서 | 타 지역 리소스 응답의 실제 `404`와 체크리스트 기대 `403`이 다름 | 백엔드·문서 |

## 분류 기준

- **크리티컬한 문제**: 기본 로컬 환경에서 시드 적용과 E2E 검증을 시작할 수 없게 만드는 문제다. 검증 흐름을 직접 차단하므로 우선 수정한다.
- **일단 고치지 않아도 될 문제**: 현재 지역 관리자 사용자 여정을 직접 차단하지 않거나 구현 변경 전에 API 정책 확정이 필요한 문제다. 관련 기능 배포 전 또는 정책 결정 후 수정한다.

## 크리티컬한 문제

### `local` DB 이름과 시드 안전장치가 맞지 않음

- 우선순위: P1
- 문제 구분: 로컬 환경·시드
- 담당 수정 대상: 백엔드
- 관련 화면: 해당 없음
- 관련 API: `GET /actuator/health`, Gradle `seedRegionAdminTestData` 작업
- 확인된 현상: `application-local.yaml`의 기본 DB는 `regional_event`지만 시드는 DB 이름에 `local`, `dev`, `test` 중 하나가 있어야 실행된다.
- 재현 절차: 별도 환경 변수 없이 `local` 프로필 설정을 사용해 `seedRegionAdminTestData -PseedProfile=local -PseedAction=apply`를 실행한다.
- 기대 결과: 기본 `local` 설정만으로 안전장치를 통과해 테스트 시드가 적용된다.
- 실제 결과: 기본 DB 이름이 안전장치 규칙을 만족하지 않아 차단된다. 이번 검증은 `SPRING_DATASOURCE_URL`을 `regional_event_local`로 덮어써 진행했다.
- 원인: 로컬 프로필의 스키마 명명 규칙과 시드 실행기의 운영 DB 오실행 방지 규칙이 서로 다르다.
- 프론트엔드 수정 방향: 해당 없음
- 백엔드 수정 방향: 로컬 DB 이름을 `regional_event_local`로 통일하고 Docker/DB 생성 설정, `application-local.yaml`, 시드 실행 문서가 모두 같은 이름을 사용하게 한다. 시드 안전장치는 완화하지 않는다.
- API 또는 문서 수정 방향: 로컬 실행 및 시드 적용 명령에 단일 DB 이름을 명시한다.
- 완료 기준: 환경 변수 우회 없이 `local` 백엔드 기동, 시드 초기화·적용, 헬스 체크 `200`이 모두 성공한다.
- 재검증 방법: 새 로컬 DB 환경에서 기본 설정만으로 시드 `reset/apply`를 실행한 뒤 `GET /actuator/health`와 지역 관리자 목록 API를 확인한다.

## 일단 고치지 않아도 될 문제

현재 사용자 여정이나 보안 경계를 직접 차단하지 않는 항목이다. 다만 문제가 해결된 것은 아니므로 정책이 확정되거나 관련 기능을 변경할 때 반드시 재검증한다.

### 예약 없는 환불 상세 조회가 여전히 `500`을 반환할 수 있음

- 우선순위: P2
- 문제 구분: 백엔드
- 담당 수정 대상: 백엔드·프론트엔드
- 관련 화면: 플랫폼 관리자 환불 실패 상세
- 관련 API: `GET /api/v1/platform-admin/refund-failures/{refundId}`
- 확인된 현상: 최신 백엔드 `dev`에서 환불 실패 목록은 예약 없는 항목을 `reservationId: null`로 정상 반환하지만, 상세 변환 로직은 여전히 예약을 필수값으로 검사한다.
- 재현 절차: 예약이 없는 환불을 목록에서 조회한 뒤 해당 환불의 상세 API를 호출한다.
- 기대 결과: 상세 API도 `200`과 `reservationId: null`을 반환하고 나머지 결제·환불·시도 정보를 표시한다.
- 실제 결과: `RefundFailureDetailInfo`가 `payment.getReservation()`을 `requireNotNull()`로 검사하고 응답 변환에서 `reservationId().toString()`을 호출해 `500`이 발생할 수 있다.
- 원인: 목록 DTO의 nullable 수정이 상세 DTO와 응답 변환까지 적용되지 않았다.
- 프론트엔드 수정 방향: 백엔드 수정 후 상세 타입을 `reservationId: string | null`로 변경하고 `null`이면 `—`를 표시한다.
- 백엔드 수정 방향: 상세의 예약 참조와 `reservationId`를 nullable로 처리하고 예약이 없을 때 예외 없이 `null`을 반환한다. 목록과 상세에 같은 계약 테스트를 추가한다.
- API 또는 문서 수정 방향: 현재 상세 API 문서의 nullable 계약과 실제 구현을 일치시킨다.
- 완료 기준: 예약 없는 환불의 목록과 상세가 모두 `200`을 반환하고 프론트에서 상세·재시도·수동 확인 흐름이 중단되지 않는다.
- 재검증 방법: 예약 없는 환불 fixture로 목록 조회 후 상세 진입, 재시도 또는 수동 확인 가능 여부를 실제 API와 브라우저에서 확인한다.

### 타 지역 리소스 응답의 실제 `404`와 체크리스트 기대 `403`이 다름

- 우선순위: P2
- 문제 구분: API 계약·문서
- 담당 수정 대상: 백엔드·문서
- 관련 화면: 지역 관리자 전체 상세 화면
- 관련 API: 예시 `GET /api/v1/region-admin/contents/920008`
- 확인된 현상: 지역 A 관리자 토큰으로 지역 B 콘텐츠 `920008`을 조회하면 `404 NOT_FOUND`가 반환되지만 현재 체크리스트는 `403`을 기대한다.
- 재현 절차: 지역 A 관리자로 로그인한 뒤 지역 B 소유 콘텐츠 상세 API를 호출한다.
- 기대 결과: 확정된 타 지역 접근 정책에 맞는 상태 코드가 문서와 구현에서 동일하다.
- 실제 결과: 백엔드는 리소스 존재 여부를 숨기는 `404 NOT_FOUND`를 반환한다.
- 원인: 백엔드는 조회 범위를 담당 지역으로 제한해 범위 밖 리소스를 찾을 수 없는 것으로 처리하지만, 검증 문서에는 권한 거부 `403`으로 작성되어 있다.
- 프론트엔드 수정 방향: 해당 없음
- 백엔드 수정 방향: `404` 은닉 정책을 유지한다면 조회·변경 엔드포인트 전반의 적용 일관성을 통합 테스트로 고정한다. `403` 정책으로 바꾸면 공통 권한 검사와 오류 매핑을 변경한다.
- API 또는 문서 수정 방향: 권장안은 조회 시 존재 여부 은닉을 위해 `404`를 유지하고 체크리스트와 API 명세를 수정하는 것이다. 변경 요청의 `403`/`404` 정책도 함께 명시한다.
- 완료 기준: 타 지역 조회·변경의 상태 코드 정책이 문서, 구현, 자동 테스트에서 일치한다.
- 재검증 방법: 지역 A/B 관리자 토큰으로 서로의 콘텐츠, 회차, 스탬프북, 미션 상세와 변경 API를 교차 호출한다.

## 공통 적용 순서

1. 로컬 DB 이름과 시드 설정을 하나의 규칙으로 통일한다.
2. 예약 없는 환불 상세의 nullable `reservationId` 계약을 백엔드 구현과 테스트에 반영한다.
3. 프론트엔드 상세 타입과 표시를 확정된 환불 계약에 맞춘다.
4. 타 지역 리소스의 `403`/`404` 정책을 확정하고 API 명세·체크리스트·자동 테스트를 일치시킨다.
5. 로컬 시드에서 지역 관리자 E2E와 예약 없는 환불 상세를 재검증한다.
